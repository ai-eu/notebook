## 1. Короткий вердикт

Проект в хорошем состоянии: архитектура понятная, 170 тестов проходят (`pytest -q`, ~27 с), явных
блокирующих багов в основном сценарии нет. Но есть три системные проблемы:

1. **Форматирование действительно переусложнено.** Одна и та же информация существует в двух
   представлениях (`transcript.json` и `formatted.txt`), а связь между ними восстанавливается заново
   на каждом открытии страницы — нечётким поиском слов по таймлайну.
2. **Есть скрытые оверхеды и утечки.** Чанки после транскрибации не удаляются, лимит размера
   загрузки не проверяется, фоновые задачи не переживают рестарт, а ошибка сети при smart-форматировании
   валит всю запись в `error`.
3. **Нет ограничения параллелизма.** Каждая загрузка запускает отдельную задачу с ffmpeg/denoise/Groq;
   несколько больших файлов одновременно могут забить CPU, память и SQLite.

## 3. P0 — надёжность, данные, корректность

### 3.1. Чанки после транскрибации не удаляются (утечка диска)

`app/services/processing.py:143-156` создаёт `folder/chunks`, но после транскрибации их никто не
удаляет. `safe_delete(chunks_dir)` есть только в `process_tts` (`:289`) и в
`cleanup_local_audio` для записей, уже ушедших в Telegram и проживших `AUDIO_RETENTION_DAYS`.

Итог: без Telegram каждая длинная запись навсегда оставляет копию аудио в чанках. Для часовой лекции
это десятки мегабайт, для архива — гигабайты.

**Что сделать:** удалять `folder/chunks` в `finally` после транскрибации (и при ошибке), как это уже
сделано для TTS. Если нужен retry без повторной нарезки — хранить чанки явно с TTL, а не «случайно».

### 3.2. Рестарт оставляет записи в `processing` навсегда

`app/routers/upload.py:21-32` и `app/routers/tts.py:26-37` держат задачи только в памяти процесса.
`app/main.py:24-28` не имеет shutdown-хука и не восстанавливает статусы. Если сервер перезапустить
во время обработки, запись останется `processing`, прогресс исчезнет, maintenance её не тронет
(он смотрит только `status == "done"`).

**Что сделать:**
- перейти на `lifespan` (заодно убрать deprecated `on_event`);
- на старте находить `pending/processing` и либо возвращать в очередь (если входной файл цел),
  либо помечать `error` с понятным сообщением;
- на shutdown отменять задачи и дожидаться их завершения с таймаутом.

Для одного uvicorn-воркера достаточно DB-статусов; для нескольких воркеров нужна очередь в БД,
иначе in-memory прогресс и maintenance loop будут дублироваться в каждом процессе.

### 3.3. Ошибка сети при smart-форматировании валит всю запись

`formatter._post_to_groq` (`:226-255`) обрабатывает только HTTP-коды. `httpx`-исключения
(`ConnectError`, `ReadTimeout`) не ловятся. Вызов `_post_to_groq` (`:282`) находится **вне**
`try` в `_split_long_sentence_with_groq`, поэтому исключение доходит до `format_transcript` →
`process_recording` → `status = "error"`.

При этом `transcript.json` уже записан (`processing.py:160`). Пользователь получает ошибку, хотя
транскрипт есть и локальное форматирование могло бы отработать.

**Что сделать:** ловить `httpx.HTTPError` и любые сбои Groq внутри smart-split, логировать и
возвращать `None` (локальный fallback). Smart-форматирование — улучшение, а не обязательный этап.

### 3.4. Лимит загрузки объявлен, но не работает

`settings.upload_max_size_mb` / `upload_max_size_bytes` (`app/config.py:19,103-104`) нигде не
используются. `app/routers/upload.py` принимает файл любого размера и сначала целиком пишет его во
временный файл.

**Что сделать:** проверять `Content-Length` и фактический размер при потоковой записи, возвращать
`413` до обработки; проверять свободное место. Иначе пользователь узнаёт о проблеме только после
долгой загрузки и конвертации.

### 3.5. Нет ограничения параллельных обработок

`_start_processing` создаёт задачу на каждый upload. Каждая задача может запустить ffmpeg, denoise,
несколько Groq-запросов и запись в SQLite. Несколько одновременных загрузок = неограниченная
нагрузка и риск `database is locked`.

**Что сделать:** глобальный `asyncio.Semaphore(MAX_CONCURRENT_JOBS)` (например, 1–2 для VPS) или
небольшая DB-очередь. Отдельно ограничить concurrency Groq-запросов.

### 3.6. Оригинал удаляется до успешной транскрибации

`processing.py:128` делает `safe_delete(original_path)` сразу после конвертации, до транскрибации.
Если Groq упал, исходник уже потерян; комментарий «Keep files for diagnostics» вводит в заблуждение,
а повторный запуск без повторной загрузки невозможен (хотя `audio.mp3` остаётся).

**Что сделать:** либо удалять оригинал после успешного `done`, либо добавить retry из `audio.mp3`
и явно описать это в статусах. Если оригинал нужен для повторной денойзации — хранить до `done`.

### 3.7. Папка загрузки может остаться сиротой

`app/routers/upload.py:94-98`: при ошибке удаляется только `tmp_path`. Если папка уже создана и
`db.commit()` упал, `folder/original.tmp` останется навсегда.

**Что сделать:** удалять созданную папку в `except` (аккуратно, только свою), либо создавать запись
в БД до перемещения файла и компенсировать при сбое.

## 4. P1 — производительность и оверхеды

### 4.1. Форматирование: 37 regex-проходов на каждое сокращение

`formatter._protect_abbreviations` (`:127-135`) в цикле делает `re.sub` для каждого элемента
`_ABBREVIATIONS` (37 штук). Это вызывается из `_split_into_sentences`, `_split_by_punctuation` и
`_split_by_clauses`, то есть на каждом абзаце/строке.

Замер на 392 тыс. символов:

| Вариант | Время |
|---|---:|
| 37 проходов (текущий) | **339.8 мс** |
| одна альтернация `(?:...|...)` | **13.2 мс** |
| само разбиение по `.!?` | 12.2 мс |

Ускорение ~**26×** только за счёт объединения сокращений в одно выражение. Это самый дешёвый и
безопасный выигрыш в проекте.

Дополнительно:
- `_split_into_sentences` (`:144-153`) и `_split_by_punctuation` (`:156-167`) — дубликаты одной
  логики; оставить одну функцию.
- `_split_by_clauses` вызывается для каждой длинной строки, а затем ещё раз внутри smart-split;
  можно один раз.

### 4.2. `build_sentence_units` пересчитывается на каждом открытии страницы

`app/routers/pages.py:57-68` синхронно читает `transcript.json` и `formatted.txt`, заново делает
`clean_transcript`, строит word timeline и ищет каждое слово в окне 25 слов (`_match_line`).
Это происходит **при каждом запросе** `/t/{id}`.

Замеры (синтетика):

| Транскрипт | `format_transcript` | `build_sentence_units` | Пик памяти |
|---|---:|---:|---:|
| 241 тыс. символов | 476 мс | 122 мс | 7.5 МБ |
| 1.206 млн символов | 2409 мс | 676 мс | 37.6 МБ |

Для часовой записи это ~0.1–0.2 с, для 4-часовой — ~0.5–0.7 с **на каждое открытие страницы**,
причём в async-обработчике, то есть с блокировкой event loop.

**Что сделать:** один раз при обработке сохранять канонический `sentences.json` (текст, start, end,
paragraph, segment_ids) и на странице просто читать его. `formatted.txt` становится производным
файлом для скачивания/архива, а не источником истины.

### 4.3. Связь «предложение ↔ тайминг» восстанавливается эвристикой

`_word_timeline` (`:441-464`) интерполирует время слов по символам внутри сегмента, а `_match_line`
(`:467-490`) ищет их в окне `ALIGN_LOOKAHEAD = 25`. При повторах, числах, переформулировках и
длинных паузах это может дать неточное или «съехавшее» выравнивание — молча, без ошибки.

**Что сделать:**
- если Groq/Whisper отдаёт word timestamps — использовать их;
- иначе строить предложения из сегментов с сохранением диапазона `segment_ids` и брать
  start/end из этих сегментов, без поиска по словам;
- сохранять результат в `sentences.json`, а не пересчитывать.

Это одновременно упрощает код и убирает целый класс логических ошибок.

### 4.4. Дублирование `formatted.txt` и `formatted-smart.txt`

`processing.py:167-168` при `SMART_FORMAT` пишет один и тот же текст в два файла. `recordings.py:193`
выбирает `formatted-smart.txt` при `smart` или глобальном `SMART_FORMAT`, а при его отсутствии может
заново запустить Groq (`:206-212`). В итоге:
- два кэша могут разойтись;
- страница всегда читает `formatted.txt`, а скачивание может читать другой файл;
- `refresh=true` позволяет повторно тратить Groq-квоту.

**Что сделать:** один кэш с версией/хэшем исходника и режима. Либо заранее считать оба варианта и
явно говорить, какой из них канонический. Smart-форматирование лучше делать один раз в обработке,
а не по запросу скачивания.

### 4.5. Перевод: последовательные батчи, новый HTTP-клиент на каждый батч

`formatter.translate_sentences` (`:558-645`):
- создаёт `httpx.AsyncClient` внутри цикла (`:614`);
- отправляет батчи строго последовательно;
- не делает retry на 429/5xx/timeout;
- размер батча — 10 предложений, то есть для 1000 предложений это ~100 запросов;
- при несовпадении числа строк молча добивает пустыми строками (`:641-643`), а лишние обрезает.

**Что сделать:**
- общий `AsyncClient` на приложение (lifespan), с лимитами соединений;
- батчи по бюджету символов/токенов, а не по 10 предложений;
- retry с `Retry-After`, ограниченный concurrency (2–3);
- просить JSON-ответ `{"translations": [...]}`, проверять длину и при mismatch повторять только
  проблемный батч; не подставлять пустые строки молча;
- кэш перевода валидировать по хэшу исходника, а не только по количеству строк (`translations.py:119-126`).

### 4.6. Транскрибация: клиент на каждый чанк, чанки последовательно

`transcriber.transcribe_file` (`:64`) создаёт новый `AsyncClient` на каждый чанк, а
`transcribe_chunks` (`:96-110`) обрабатывает чанки по одному. Для 10–20 чанков это лишние TLS
handshake и полностью последовательное ожидание.

**Что сделать:** общий клиент и настраиваемый concurrency (по умолчанию 1–2 с учётом rate limit
Groq), retry на 429/5xx для каждого чанка, прогресс под локом. Это может дать кратный выигрыш на
длинных записях, но только с осторожным лимитом.

### 4.7. Нарезка перекодирует уже готовый MP3

`converter.split_audio` (`:160-187`) для каждого чанка запускает ffmpeg с декодированием и повторным
кодированием. При этом в проекте уже есть `split_mp3_by_size` (`:234-279`), который режет по
границам MPEG-кадров байт-в-байт. `audio.mp3` — уже готовый MP3 (или passthrough), поэтому
перекодирование чаще всего не нужно.

**Что сделать:** сначала пробовать `split_mp3_by_size` (в `to_thread`), а ffmpeg-нарезку оставить
fallback для нестандартных потоков. Экономия CPU и отсутствие потерь качества на стыках.

### 4.8. Плеер: O(n) на каждый `timeupdate`

`static/js/player.js:135-146` линейно ищет активное предложение, а `highlightSentence` (`:180-195`)
на каждом тике снимает класс со **всех** `.sentence-line` и делает `querySelector`. При 1000–1500
строках это тысячи DOM-операций в секунду.

**Что сделать:** бинарный поиск по `start`, хранить `lastIndex` и переключать класс только у
предыдущего/текущего элемента.

### 4.9. Список записей: N файловых `stat` и нет пагинации

`recordings.list_recordings` (`:63-74`) отдаёт все записи, а `_recording_to_dict` (`:25-38`) делает
`(folder / "formatted.txt").exists()` для каждой. При тысяче записей это тысяча обращений к диску на
каждый `loadRecordings()`, который вызывается после каждого сохранения тегов/удаления/завершения
обработки.

**Что сделать:** пагинация/лимит, а `txt_ready` хранить в БД (флаг обновляется при обработке) или
считать одним проходом. Для списка не нужен `include_transcript`.

### 4.10. Страница дублирует текст в HTML

`templates/transcript.html:67-68` всегда встраивает полный `window.TRANSCRIPT` (все сегменты) **и**
`window.SENTENCE_UNITS`. Если units есть, `TRANSCRIPT` нужен только как fallback. Для длинной
записи это лишние сотни килобайт HTML и память браузера.

**Что сделать:** не отдавать `TRANSCRIPT`, когда есть `SENTENCE_UNITS`; fallback загружать лениво
отдельным запросом. Заодно проверить, нужен ли фронтенду `GET /api/recordings/{id}` с полным
транскриптом — по коду он не используется.

### 4.11. Денойз держит всё аудио в памяти

`denoiser.py:76-88` читает весь файл в `float32` и прогоняет `noisereduce` целиком. Для 22 кГц моно
это ~317 МБ на час, плюс копия результата и WAV. Для 3-часовой записи — около 1–2 ГБ. Денойз выключен
по умолчанию, но при включении это бомба замедленного действия.

**Что сделать:** либо ffmpeg-фильтр `afftdn` (потоково, низкая память), либо обработка блоками с
перекрытием. Как минимум — явный лимит длительности/памяти и понятная ошибка.

### 4.12. CPU-работа и файловый I/O в async-обработчиках

`format_transcript` вызывается внутри `process_recording` (async task), `build_sentence_units` — прямо
в `pages.transcript_page`, чтение/запись файлов — синхронное. На длинных записях это блокирует event
loop и задерживает status-polling/другие запросы.

**Что сделать:** минимум `await asyncio.to_thread(...)` для CPU/IO-операций; в идеале — вынести
форматирование в один этап обработки и сохранять результат (см. 4.2).

### 4.13. `clean_transcript` вызывается многократно

Один и тот же транскрипт очищается в `transcribe_file` (`:81`), `format_transcript` (`:397`),
`build_sentence_units` (`:535`), `_recording_to_dict` (`:42`) и на странице (`pages.py:62`).
Это дешёвая, но бессмысленная работа и риск расхождений, если правила очистки поменяются.

**Что сделать:** чистить один раз при приёме результата от Whisper и хранить уже очищенный
`transcript.json`; для старых файлов — одноразовая миграция/ленивая очистка.

## 5. P2 — логика, двусмысленность, эксплуатация

### 5.1. «Предложение» — это на самом деле строка отображения

`_split_by_clauses` (`:170-181`) режет длинное предложение по запятым, и полученные фрагменты
становятся отдельными units. Затем:
- страница показывает их как предложения;
- перевод переводит их как отдельные предложения;
- тайминги выравниваются по фрагментам.

Фрагмент «..., because ...» — не самостоятельное предложение, поэтому перевод и подсветка
деградируют. Плюс `MAX_LINE_LENGTH = 250` — это ограничение отображения, а не смысловая граница.

**Что сделать:** разделить «каноническое предложение» и «строку для показа». Максимальную длину
решать переносом/CSS или отдельным полем `display_text`, а переводить целые предложения. Если
длинную строку всё же режем — хранить `parent_sentence_id`.

### 5.2. Пробелы в разбиении на предложения

`_SENTENCE_RE = ([.!?]+["'»]?)\s+(?=\S)` и список сокращений не покрывают:
- инициалы: `J. Smith`, `J. R. R. Tolkien`;
- `U.S.`, `a.m.`, `p.m.`, `Ph.D.`;
- десятичные числа с пробелом/неразрывным пробелом;
- сокращения не из списка.

Будут ложные разрывы. Плюс `_protect_abbreviations` требует границы `(?<!\S)...(?!\S)`, поэтому
`etc.` в конце строки/перед кавычкой может не защититься.

**Что сделать:** добавить тест-кейсы и либо расширить список, либо перейти на один проход с
учётом контекста (следующий токен с заглавной/цифрой, известные шаблоны). Без тяжёлых NLP-зависимостей.

### 5.3. Кэш перевода и конкурентные запросы

- Валидация только по количеству строк (`translations.py:119-126`): если текст изменился, но число
  строк совпало, отдастся устаревший перевод.
- Два одновременных запроса на один язык сделают два Groq-вызова и будут писать один файл без лока;
  возможен частичный/битый файл.
- `DELETE /api/translate/{id}` (`:153-180`) не проверяет `lang` по списку разрешённых, в отличие от
  GET. Сейчас префикс `formatted-` спасает от прямого path traversal, но это хрупко.
- `LANGUAGE_NAMES` (`formatter.py:19-24`) фиксирован на 4 языка, а `TRANSLATION_TARGET_LANGUAGES`
  настраивается; для нового языка в UI будет код вместо названия.

**Что сделать:** per-(recording, lang) lock; писать через temp+replace; хранить `source_hash` и
`prompt_version`; валидировать `lang` в DELETE; вынести названия языков в конфиг/справочник.

### 5.4. Гонка в прогрессе TTS

`processing.py:250-251`: `get_tts_progress()` → `set_tts_progress(done + 1, ...)` без лока.
При `tts_concurrency > 1` два корутины могут прочитать одно значение и потерять обновление.
На результат синтеза не влияет, но прогресс в UI врёт.

**Что сделать:** `asyncio.Lock` или отдельный счётчик/`asyncio.Queue`; инкремент атомарно.

### 5.5. Приложение зависит от текущего каталога

`config.data_dir_absolute` (`:99-100`) использует `Path.cwd()`, `database_url` относительный,
`StaticFiles(directory="static")`, `Jinja2Templates(directory="templates")`, `static_version` —
тоже относительные. `.env` при этом ищется относительно файла проекта. Запуск не из корня проекта
приведёт к другому `data/`, другой БД и отсутствию шаблонов.

**Что сделать:** один `BASE_DIR = Path(__file__).resolve().parent.parent` и использовать его для
`data`, `db`, `templates`, `static`; в `.env` разрешить абсолютные пути.

### 5.6. SQLite: нет WAL, busy_timeout и foreign_keys

`database.py:6-10` создаёт engine без PRAGMA. Следствия:
- фоновые записи (upload/status/archive) могут ловить `database is locked`;
- `ondelete="CASCADE"` в моделях не сработает на уровне БД без `PRAGMA foreign_keys=ON`
  (ORM-каскады работают, но не все сценарии);
- список записей фильтруется по `user_id` без индекса, сортировка по `created_at` — тоже.

**Что сделать:** event-listener на connect с `journal_mode=WAL`, `busy_timeout=5000`,
`foreign_keys=ON`; добавить `Index("ix_recordings_user_created", "user_id", "created_at")`.
Для миграций либо Alembic, либо версионированная таблица (текущий `_add_missing_columns` не создаёт
индексы/уникальные ограничения и не умеет NOT NULL).

### 5.7. Нет очистки сессий и device-invite

Истёкшие `Session` и `DeviceInvite` нигде не удаляются глобально (`auth.list_user_sessions` только
фильтрует). Таблицы медленно растут.

**Что сделать:** добавить purge в maintenance loop (раз в сутки).

### 5.8. Мёртвый/лишний код и конфиг

- `GET /api/recordings/{recording_id}` с полным транскриптом не используется фронтендом.
- `settings.upload_max_size_bytes` — мёртвый (см. 3.4).
- `_split_by_punctuation` — дубликат `_split_into_sentences`.
- `formatted-smart.txt` — дубликат (см. 4.4).
- `cache._locks` растёт на одну запись на каждый `recording_id` и не очищается.
- `auth._login_failures` очищается только при обращении; при большом числе IP словарь растёт.

### 5.9. Смешанные языки интерфейса

`translation.js` пишет ошибки по-русски, остальной UI — по-английски, часть сообщений — по-русски.
Для пользователя это выглядит небрежно. Стоит выбрать один язык или вынести строки в шаблоны.

### 5.10. Безопасность (не срочно, но стоит знать)

- Groq-ключи хранятся в БД открытым текстом (задокументировано). При утечке БД утекают ключи.
  Можно шифровать at rest ключом из окружения.
- Rate limit логина in-memory и per-worker; при нескольких воркерах он слабее.
- `GET /api/translate` (список языков) не требует авторизации — небольшой information leak.
- CSRF: state-changing запросы защищены `SameSite=lax` в основном сценарии, но стоит осознанно
  зафиксировать это в документации.

## 6. Как я бы упростил форматирование (целевая схема)

Сейчас:

```
Whisper segments -> transcript.json
                 -> clean_transcript (повторно)
                 -> paragraphs by gap
                 -> split sentences (37 regex passes)
                 -> split long lines by commas
                 -> optional Groq per clause
                 -> formatted.txt (+ formatted-smart.txt)
страница:        -> clean_transcript снова
                 -> split formatted.txt снова
                 -> word timeline + fuzzy matching
                 -> units -> HTML
перевод:         -> split formatted.txt снова
                 -> translate batches
                 -> formatted-<lang>.txt
```

Предлагаю:

```
Whisper segments (+ word timestamps, если доступны)
  -> clean_transcript ОДИН раз
  -> paragraphs by pause
  -> sentence splitter ОДИН раз (одна regex-альтернация сокращений)
  -> sentences.json  <-- канонический источник истины
       [{text, start, end, paragraph, segment_ids}]
  -> formatted.txt   <-- производный файл для скачивания/архива
  -> страница/плеер/перевод читают sentences.json
  -> перевод: индекс предложения + source_hash + lang
```

Что это даёт:

- страница не делает тяжёлую работу: чтение JSON вместо `O(words × lookahead)`;
- тайминги точные и воспроизводимые, без эвристики;
- перевод и подсветка работают с настоящими предложениями, а не с обрезками по запятым;
- `formatted.txt` и `formatted-smart.txt` перестают быть конкурентными источниками истины;
- проще тестировать: форматтер — чистая функция `segments -> sentences`, без файлов и сети.

Компромисс: `sentences.json` — новый формат, нужна ленивая миграция для старых записей. Но это
дешевле, чем поддерживать два представления и fuzzy-выравнивание.

## 7. План работ

### Этап 0 — быстрые и безопасные улучшения

1. Удалять `folder/chunks` в `finally` после транскрибации.
2. Ловить `httpx.HTTPError` в smart-format и делать локальный fallback.
3. Проверять `upload_max_size` при загрузке (413) + чистить папку при ошибке.
4. Глобальный семафор на обработку (1–2 задачи).
5. Объединить сокращения в одну regex-альтернацию; удалить дублирующий splitter.
6. Убрать дублирование `formatted-smart.txt` или сделать один кэш с версией.
7. `delete_translation`: валидировать `lang`.
8. `asyncio.to_thread` для чтения/форматирования на странице (как временная мера до `sentences.json`).
9. Плеер: бинарный поиск + обновление только двух элементов.
10. `lifespan` + восстановление `processing` на старте.
11. PRAGMA WAL/busy_timeout/foreign_keys + индекс `(user_id, created_at)`.
12. Компактный `json.dumps` для `transcript.json`.

### Этап 1 — ядро: убрать пересчёт форматирования

1. Ввести `sentences.json` и генерировать его в `process_recording`/`process_tts`.
2. Перевести страницу, плеер и перевод на `sentences.json`.
3. `formatted.txt` генерировать из `sentences.json`; smart-режим — отдельное поле/версия.
4. Убрать fuzzy `_word_timeline`/`_match_line` (или оставить только fallback для старых записей).
5. Общий `httpx.AsyncClient` для Groq/Telegram, retry на 429/5xx/timeout.
6. Перевод: JSON-ответ, батчи по токенам, ограниченный concurrency, кэш по `source_hash`.
7. Транскрибация чанков: настраиваемый concurrency + retry.
8. Нарезка чанков через `split_mp3_by_size`, ffmpeg — fallback.

### Этап 2 — эксплуатация и качество

1. DB-очередь задач или явное ограничение «один воркер»; прогресс в БД, если воркеров больше одного.
2. Пагинация списка записей, `txt_ready` в БД.
3. Alembic (или версионированные миграции) вместо самописного `_add_missing_columns`.
4. Purge истёкших сессий/инвайтов в maintenance.
5. `BASE_DIR` для data/db/templates/static.
6. Добавить `ruff` + `mypy`/`pyright` в dev-зависимости и CI.
7. Опционально: шифрование Groq-ключей at rest, rate limit на upload/TTS.

### Чего бы я не делал

- Не тащить Redis/Celery для одного VPS и одного воркера: DB-статусы + семафор достаточны.
- Не менять SQLite на Postgres без реальной необходимости.
- Не добавлять тяжёлые NLP-библиотеки ради split-а; одной аккуратной regex/state-machine хватает.
- Не параллелить Groq «на максимум»: rate limit важнее, concurrency должна быть настраиваемой.

## 8. Тесты, которые стоит добавить

1. Форматтер не теряет и не дублирует слова: нормализованные bag-of-words до/после равны.
2. Сокращения и инициалы: `Dr. Smith`, `J. R. R. Tolkien`, `U.S.`, `a.m.`, `3.14`, URL.
3. Длинное предложение > `MAX_LINE_LENGTH`: поведение с Groq и без, без падения.
4. Groq: 429 с `Retry-After`, 500, timeout, `ConnectError` → локальный fallback, статус `done`.
5. Smart-format не валит запись, если Groq недоступен.
6. `build_sentence_units`: монотонные `start/end`, повторы слов, перефразированные строки.
7. `sentences.json`: миграция старой записи, версия формата, fallback при отсутствии.
8. Перевод: меньше/больше строк, перенос строки внутри перевода, конкурентные запросы, stale cache
   при том же количестве строк, невалидный `lang` в DELETE.
9. Upload: файл больше лимита → 413 и отсутствие мусора; сбой `db.commit()` → папка удалена.
10. Рестарт: `processing` на старте → `error`/requeue; shutdown отменяет задачи.
11. Чанки удаляются после успеха и после ошибки.
12. Семафор: одновременно не больше N обработок.
13. TTS: конкурентный прогресс не теряет обновления.
14. DB: PRAGMA/индексы/миграция колонок.
15. Опционально: perf-тест на 1.2 млн символов с порогом (пометить `slow`).

## 10. Итог

Самое важное — не «микробенчмарки», а устранение двух источников сложности:

1. **Один канонический результат форматирования** (`sentences.json`) вместо пересчёта и fuzzy-
   выравнивания на каждом запросе.
2. **Одна ответственная точка за жизнь фоновой задачи** (lifespan + восстановление + семафор),
   вместо набора in-memory словарей и `create_task` без учёта рестарта.

После этого форматирование станет линейным и предсказуемым, страница перестанет блокировать event
loop, а длинные записи — оставлять мусор и зависать в `processing`.
